Citesmith 再構築計画

2026-11-07 作成。決定事項は docs/decisions.md に記録する。

目標

  1. 対応ページに Citesmith ボタンを置く
  2. 指定したファイル名で PDF をダウンロードする
  3. BibTeX をクリップボードにコピーする

対象：ScienceDirect (Elsevier)、Springer、Nature、Wiley、arXiv

調査結果：各サイトが提供している情報

5サイトとも HTML を細かく解析する必要はない。どのサイトでも次のいずれかが使える。

  • citation_* メタタグ：Google Scholar 向けの標準タグ。タイトル、著者、日付、DOI、PDF の URL が入っている。
  • サイト独自の BibTeX エクスポート：各サイトの「Cite」ボタンが内部で使っている URL。
  • DOI コンテントネゴシエーション：https://doi.org/<DOI> に Accept: application/x-bibtex を付けて取得すると BibTeX が返る（Crossref と DataCite が対応）。DOI があればサイトに関係なく使える。

BibTeX の取得元ごとの特徴

  • サイト独自のエクスポート：アブストラクトやキーワードまで入っていて情報が多い。書式はサイトごとに違う。Springer は "…" で値を囲み、ScienceDirect の doi には https://doi.org/ が付く。
  • doi.org：書式が全サイトで共通。ただし中身は出版社が Crossref に登録した情報次第で、試した Wiley の論文ではタイトルと著者が欠けていた。そのため、サイト独自のエクスポートが使えないときの予備にする。
  • arXiv：/bibtex/<id> の year は最新版の年になる（1706.03762 では 2017 ではなく 2023）。初版の年がよければ DataCite（doi.org/10.48550/arXiv.<id>）を使うか、メタタグの日付で上書きする。
  • Elsevier API と Springer Nature API は API キーが必要なので使わない。

設計方針

content script（ページ側）

サイトの判定、ボタンの設置、メタタグの読み取り、クリップボードへのコピー

⇄

service worker（background）

BibTeX の取得、ファイル名の生成、chrome.downloads.download({url, filename})

  • ファイル名はメタタグから作る。著者、年、タイトルは citation_* から取り、BibTeX は解析せずにそのままコピーする。サイトごとに書式が違う BibTeX を正規表現で解析する必要がなくなる。メタタグがないサイトだけ、doi.org の CSL-JSON（構造化済みの JSON）で補う。
  • ダウンロードは chrome.downloads で行う。今の <a download> では、別ドメインの PDF（ScienceDirect など）でファイル名の指定が無視される。downloads 権限はすでに宣言済み。
  • サイトごとの差は小さなアダプタにまとめる。各サイトの処理は「識別子、BibTeX の URL、PDF の URL、ボタンの置き場所」を返すだけにし、残りの処理は全サイトで共通にする。
  • ファイル名に使えない文字（/ \ : * ? " < > |）は除去する。

Node を使ったデバッグ環境

有効です。ただし使い道を分けます。

向いている

  • BibTeX の取得元（API）を直接たたく確認：arXiv、Nature、Springer の BibTeX、ScienceDirect の cite API、doi.org
  • ファイル名テンプレートや文字の除去など、純粋なロジックのテスト（node --test、追加の依存なし）
  • ブラウザで保存した HTML を使ったメタタグ抽出のテスト

向いていない

  • ScienceDirect、Springer、Wiley の記事ページそのもの（403 やボット判定で取得できない）
  • ログインや機関認証が必要な PDF の取得
  • ボタンの見た目やクリック動作

これらは Chrome に読み込んで確認する。

ロジックを ES モジュールにしておくと、service worker（"type": "module"）と Node の両方から同じコードを使える。構成案：

src/
  sites/       サイトごとのアダプタ
  filename.js  テンプレート展開、文字の除去
  background.js
  content.js
test/          node --test
  fixtures/    ブラウザで保存した HTML
scripts/
  probe.mjs    各サイトの API を実際にたたいて結果を表示する

実装の順番

  1. 土台：ディレクトリ構成、node --test、scripts/probe.mjs、ファイル名生成。既存のバグ（ボタンが置けない、Wiley/arXiv で TypeError）はこの段階で消える。
  2. arXiv と Nature：Node だけで BibTeX の取得まで確認できる2サイトで、ボタン、ダウンロード、コピーの一連の流れを先に完成させる。
  3. ScienceDirect と Springer：アダプタを追加する。ScienceDirect は PDF の URL の取り方をブラウザで確認する。
  4. Wiley：Cloudflare があるので、すべてブラウザで確認する。
  5. 追加機能（下の候補から選ぶ）

Chrome での調査結果（2026-11-07）

一時プロファイルの Chrome を DevTools Protocol で操作して調べた。

  • Springer：サーバー側で描画済み。citation_author は「姓, 名」。ボタンの置き場所は .app-article-masthead__buttons（a.c-pdf-download__link は2つあり、2つ目は追従バー）。
  • Wiley：ウィンドウを表示した Chrome なら Cloudflare を通過できる。citation_author は「名 姓」。ボタンの置き場所は nav.coolBar .coolBar__second。
  • ScienceDirect：自動操作の Chrome では記事ページが 403 になる。メタタグ、PDF の URL、ボタンの置き場所は、普段使いの Chrome で1本手動で確認する必要がある。cite API は取得できた。

まだ確認が必要なこと

  • ScienceDirect の記事ページのメタタグ、PDF の直接 URL、ボタンの置き場所（手動）
  • chrome.downloads で取得するとき、機関認証の Cookie が付くか（ScienceDirect、Wiley）
  • BibTeX の取得に時間がかかっても、クリップボードへのコピーが成功するか（Chrome はクリック直後の数秒しかコピーを許可しない）
